## 1. الهدف

تحويل النظام من واجهة مؤسسية متقدمة تجمع بين البيانات التجريبية والتكامل الجزئي مع Supabase إلى نظام موارد بشرية إنتاجي، آمن، قابل للتدقيق، ومهيأ للتشغيل الفعلي في بيئة سعودية، مع الحفاظ على Material Design 3 ودعم العربية RTL والإنجليزية LTR.

لا تُعد أي شاشة مكتملة إنتاجيًا لمجرد اكتمال تصميمها؛ الإكمال يعني أن القراءة والإنشاء والتعديل والاعتماد والحذف أو الأرشفة — بحسب صلاحية المستخدم — محفوظة فعليًا، ومحمية بسياسات RLS، ومسجلة في سجل التدقيق، ومغطاة باختبارات آلية.

## 2. نتيجة مراجعة الحالة الحالية

### نقاط القوة الحالية

- واجهة عربية متقدمة ومتجاوبة مبنية بـ React 19 وTypeScript وMaterial Design 3.
- تسجيل دخول حقيقي عبر Supabase، مع عدم وجود تسجيل ذاتي من شاشة الدخول.
- مخطط قاعدة بيانات واسع ومجموعة migrations للأمان والوحدات التشغيلية.
- طبقات Repository وServer Functions لجزء مهم من الموظفين والطلبات والحضور والرواتب.
- ربط فعلي مبدئي لوحدات المنشأة، الموظفين، الطلبات، الإجازات، الحضور، الرواتب، المصروفات، الأداء، التوظيف، العهد والوثائق.
- GitHub Actions يعمل تلقائيًا ويشغّل TypeScript وESLint والتغطية والبناء واختبارات Playwright على Desktop وPixel 7.
- آخر Workflow تمت مراجعته ناجح بالكامل.

## 4. مراحل التنفيذ

### المرحلة 0 — بوابة أمان التشغيل P0

الهدف: منع أي نشر إنتاجي مضلل أو فقد صامت للبيانات.

- ربط ظهور Demo بـ `VITE_ENABLE_DEMO_MODE` ومنعه افتراضيًا في Production.
- استبدال ادعاء "التوافق الكامل" بصياغة محايدة حتى توقيع اعتماد الامتثال.
- إضافة فحص Startup يمنع تشغيل Live إذا كانت إعدادات Supabase وهمية أو ناقصة.
- تحويل عمليات الحفظ إلى `async` بحالات Loading/Success/Error واضحة مع Rollback أو إعادة Fetch مؤكدة.
- منع رسائل النجاح قبل تأكيد الحفظ من الخادم.
- إضافة شاشة حالة اتصال صغيرة للمسؤولين فقط.
- إنشاء Migration smoke test واختبار أن جميع الجداول المطلوبة وسياسات RLS مطبقة.
- إضافة اختبارات Auth حقيقية: دخول، خروج، جلسة منتهية، حساب بلا صلاحية، وإعادة تعيين كلمة المرور.

معيار الخروج:

- لا يظهر Demo في Build الإنتاج.
- أي فشل حفظ يظهر للمستخدم ولا يظل كتغيير وهمي في الواجهة.
- إعادة تحميل الصفحة بعد كل عملية CRUD تعيد نفس البيانات.
- اختبار RLS يثبت منع الموظف من قراءة رواتب أو وثائق موظف آخر.

### المرحلة 1 — الأساس المعماري والبيانات

- تقسيم `AppContext` إلى Domains مستقلة باستخدام React Query: Organization, Employees, Time, Payroll, Talent, Governance.
- توحيد DTO/Mapper بين TypeScript وPostgreSQL وإزالة التحويلات غير الآمنة.
- اعتماد TanStack Router لمسارات فعلية مثل `/employees/:id` و`/payroll/runs/:id`.
- إضافة Zod validation على كل Form وServer Function.
- توحيد Pagination/Filtering/Sorting على الخادم بدل تحميل جميع السجلات.
- إضافة Transactions/RPC للعمليات المركبة مثل الاعتماد والراتب والتحويل من مرشح إلى موظف.
- إضافة Error codes ورسائل عربية/إنجليزية قابلة للتتبع.

معيار الخروج:

- لا توجد شاشة تعتمد على State عالمي ضخم أو نسخة Mock في Live mode.
- الروابط العميقة تعمل بعد Refresh ويمكن حمايتها بالصلاحيات.
- الاستعلامات الكبيرة تستخدم Pagination وفهارس موثقة.

### المرحلة 2 — الهوية والصلاحيات والحوكمة

- إدارة المستخدمين بالدعوات فقط، مع ربط الحساب بسجل موظف محدد.
- نسيت كلمة المرور وتغييرها وسياسة قوة كلمة المرور.
- MFA للمسؤولين والرواتب والمالية.
- إدارة Role Definitions وPermissions وAssignments بالكامل.
- تطبيق Data Scope: Self, Team, Department, Subsidiary, All داخل SQL/RLS.
- فصل الواجبات: مُعد الراتب لا يعتمد نفس المسير، وصاحب الطلب لا يعتمد طلبه.
- جلسات وأجهزة نشطة، إلغاء الجلسة، وحدود لمحاولات الدخول.
- اختبارات مصفوفة صلاحيات لكل دور ولكل جدول حساس.

### المرحلة 3 — المنشأة والموظفون والوثائق

- إكمال CRUD والأرشفة للكيانات التنظيمية والوظائف ومراكز التكلفة والمواقع.
- قواعد سلامة الهيكل: لا دورة إدارية، لا حذف لوحدة مرتبطة، ونقل الموظفين قبل الأرشفة.
- إكمال Employee Lifecycle من العرض الوظيفي حتى إنهاء الخدمة.
- استيراد موظفين مع Dry Run وتقرير أخطاء وعدم تكرار.
- Supabase Storage للهوية والعقود والشهادات، مع مسارات خاصة وسياسات تنزيل.
- Expiry Engine للهوية والإقامة والجواز والعقد والشهادات.
- سجل تاريخي للوظيفة والراتب والمدير والوحدة.

### المرحلة 4 — الحضور والإجازات والطلبات

- جدولة الورديات والإسناد الجماعي والتعامل مع الورديات الليلية.
- استيراد Punches خام ومعالجة Idempotent إلى Attendance Records.
- Geofence دقيق، مع حفظ الإحداثيات والدقة والمصدر ومبرر الاستثناء.
- دورة كاملة لتصحيح البصمة والعمل الإضافي محفوظة ومربوطة بالاعتمادات.
- محرك إجازات Transactional يراعي العطلات وعطلة الأسبوع ونصف اليوم وتداخل الطلبات.
- SLA وتصعيد وتفويض فعلي لمسارات الاعتماد.
- تقارير الحضور: إحصائي، تفصيلي، شامل، وتأخير يومي.

### المرحلة 5 — الرواتب والمالية

- اعتماد Salary Profile بتاريخ سريان بدل الاعتماد على قيمة واحدة حالية.
- Pipeline واضح: Draft → Calculated → Reviewed → Approved → Locked → Paid.
- منع التكرار وإعادة التشغيل الآمنة وتوثيق نسخة مدخلات كل مسير.
- اختبارات Golden Payroll لحالات: تعيين/إنهاء منتصف الشهر، غياب، إضافي، إجازة دون راتب، سلفة، Bonus، GOSI.
- قسيمة راتب PDF عربية/إنجليزية ومحمية للمستخدم نفسه.
- WPS/SIF مع Validation للآيبان والبنك والإجماليات، ثم UAT مع البنك.
- دورة السلف والأقساط والمخالصة والترحيل المحاسبي.
- المصروفات والفواتير والضريبة والموافقات والترحيل.

تنبيه امتثال: أي قواعد لنظام العمل أو GOSI أو WPS يجب اعتمادها من المختص القانوني/المالي للمنشأة قبل التشغيل، حتى لو نجحت الاختبارات البرمجية.

### المرحلة 6 — المواهب والتوظيف والعهد

- إكمال الأداء 360° والأهداف والمعايرة وخطط التطوير.
- Workforce Planning وربط الميزانية بالشواغر الفعلية.
- ATS متكامل من الوظيفة حتى العرض والتوظيف بضغطة واحدة داخل Transaction.
- مواعيد مقابلات وقوالب بريد وتقييم موحد وسجل اتصالات.
- دورة عهد كاملة: شراء، مخزون، إسناد، صيانة، استرجاع، شطب وإخلاء طرف.
- إدارة سياسات ووثائق بإصدارات وإقرارات قابلة للإثبات.

### المرحلة 7 — التقارير والتكاملات والتدقيق

- طبقة تقارير منفصلة بفلترة على الخادم وData Scope.
- قوالب XLSX/PDF وجدولة وتسليم آمن.
- قيود محاسبية قابلة للمراجعة والإلغاء العكسي، لا الحذف.
- Webhooks موقعة مع Retry وIdempotency وسجل تسليم.
- Event Outbox للإشعارات والتكاملات.
- سجل تدقيق Append-only مع حظر UPDATE/DELETE واختبار ذلك.
- تكامل واحد فعلي يبدأ حسب أولوية العميل، ثم تعميم Connector framework.

### المرحلة 8 — تجربة المستخدم والجوال والإتاحة

- مراجعة Material Design 3 وتوحيد Tokens والمكونات والحالات الفارغة والأخطاء والتحميل.
- رفع الحد الأدنى للخطوط العربية ووضوح التباين وتقليل ازدحام الجداول.
- دعم Keyboard وScreen Reader وWCAG 2.2 AA.
- PWA قابلة للتثبيت مع Offline آمن للصفحات غير الحساسة فقط.
- تحسين الأداء: Route splitting، Virtualized tables، صور وملفات محسنة، وميزانية Bundle.
- Visual Regression للواجهات الأساسية Desktop/Mobile وRTL/LTR وLight/Dark.

### المرحلة 9 — الجاهزية للإطلاق

- بيئات منفصلة: Development، Staging، Production مع أسرار وقواعد بيانات مستقلة.
- نسخ احتياطي مجدول واختبار Restore موثق.
- مراقبة الأخطاء والأداء وHealth Checks وتنبيهات التشغيل.
- اختبارات تحميل وأمان وفحص Dependencies وSecrets وSAST.
- UAT بسيناريوهات واقعية وموافقات مكتوبة من HR والمالية والإدارة.
- خطة Migration للبيانات وخطة Rollback وRunbook للدعم.
- إطلاق تدريجي Pilot ثم تعميم، مع Hypercare بعد الإطلاق.

| Migration     | تطبيق القاعدة من الصفر ثم ترقية نسخة سابقة             | لا فشل ولا فقد بيانات والمخطط مطابق للـTypes         |
| RLS           | كل دور × كل عملية × كل جدول حساس                       | Deny by default ولا تسريب أفقي أو تصعيد صلاحيات      |
| E2E Demo      | التنقل والعرض السريع                                   | يظل سريعًا ولا يتصل بالإنتاج                         |
| E2E Live      | دخول حقيقي وحفظ ثم Refresh واعتماد متعدد الأدوار       | نجاح التدفقات الحرجة على قاعدة Staging معزولة        |
| Accessibility | axe + Keyboard + Screen Reader smoke                   | صفر أخطاء Critical/Serious في الشاشات الحرجة         |
| Visual        | Desktop/Mobile وRTL/LTR وLight/Dark                    | لا تغييرات غير معتمدة في الصور المرجعية              |
| Performance   | بيانات كبيرة ومسيرات ورواتب وتقارير                    | حدود زمنية متفق عليها ولا تحميل كامل غير ضروري       |
| Security      | SAST، Dependency scan، Secrets scan واختبار اختراق     | صفر Critical/High مفتوح قبل الإنتاج                  |

ملاحظة: نسبة التغطية الحالية المرتفعة تخص مجموعة ملفات حرجة محددة في `vitest.config.ts`، وليست نسبة تغطية شاملة لكل واجهات ومستودعات النظام.

## 6. Definition of Done لكل ميزة

لا تغلق أي بطاقة تطوير قبل تحقق البنود التالية:

- تحقق Zod في العميل والخادم عند الحاجة.
- قراءة وكتابة حقيقية بدون Mock في Live mode.
- RLS وصلاحيات واجهة وخادم متطابقة.
- Audit event للعمليات الحساسة.
- Loading وEmpty وError وSuccess states واضحة.
- منع الضغط المتكرر وIdempotency للعمليات المالية أو المركبة.
- اختبار Unit/Integration/E2E مناسب.
- دعم RTL/LTR وDesktop/Mobile والوضعين الفاتح والداكن.
- لا أخطاء TypeScript أو ESLint أو Build أو GitHub Actions.
- Migration قابلة للتطبيق والاسترجاع التشغيلي موثق عند التغيير الحساس.
- توثيق المستخدم/المشغل محدث.

## 8. أول دفعة تنفيذية معتمدة

ستبدأ الدفعة التالية مباشرة بالترتيب الآتي:

1. **Production Mode Guard**: ربط Demo بالبيئة، منع إعدادات Supabase الوهمية، وإظهار خطأ إعداد واضح.
2. **Reliable Mutations**: واجهة async موحدة للحفظ مع منع التكرار وRollback ورسائل خطأ دقيقة.
3. **Live Test Harness**: Supabase محلي/معزول، تطبيق migrations من الصفر، Seed اختباري، واختبارات RLS.
4. **Workflow Persistence**: حفظ تفويضات الصلاحيات وحذف/أرشفة مسارات الاعتماد وتصحيحات الحضور والإضافي.
5. **Live E2E Smoke**: دخول فعلي، إنشاء موظف/طلب، Refresh، اعتماد بدور آخر، والتحقق من منع الوصول غير المصرح.

## 9. آلية المتابعة والتسليم

- كل دفعة تكون Commit مستقلة قابلة للمراجعة ومتزامنة مع Lovable بدون Force Push أو إعادة كتابة التاريخ.
- لا يُدمج أي تغيير يفشل GitHub Actions.
- تحديث جدول الوحدات وهذه الخطة بعد كل دفعة.
- إرفاق نتيجة الاختبارات ورابط Workflow في تسليم كل دفعة.
- نشر Staging أولًا، ثم Production بعد UAT وموافقة مسؤول النظام.

## 10. مؤشرات النجاح

- 100% من العمليات الحرجة محفوظة بعد Refresh ولا تعتمد على Mock في Live mode.
- 100% من الجداول الحساسة مغطاة بمصفوفة RLS آلية.
- صفر ثغرات Critical/High مفتوحة قبل الإنتاج.
- صفر فشل في TypeScript وLint وUnit وIntegration وE2E على `main`.
- 100% من مسارات الرواتب والاعتمادات المالية Idempotent وقابلة للتدقيق.
- WCAG 2.2 AA للشاشات الحرجة.
- نجاح Restore فعلي من Backup في بيئة معزولة.
- اكتمال UAT واعتماد HR والمالية والإدارة قبل الإطلاق العام.
