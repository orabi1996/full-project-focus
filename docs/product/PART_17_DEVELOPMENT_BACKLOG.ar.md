## 4. مثال قابل للنقل

**TEN-001** — As a platform engineer, I want to store tenant memberships with database isolation, so that new features have a trusted tenant boundary.

- **Given:** شركتان وعضوان فعالان في قاعدة اختبار. **When:** يقرأ عضو الشركة A السجل بصفة authenticated. **Then:** يرى شركته وعضويته وإعداداتها فقط.
- **Given:** عضو مستخدم عادي أو مجهول. **When:** يحاول إدراج عضوية أو تغيير tenant_id أو حذف سجل. **Then:** تمنع قاعدة البيانات الكتابة ولا تمنح عضوية جديدة.

المهام: migration توسعية؛ grants/RLS؛ اختبارات فعلية للأدوار؛ توثيق provisioning والتراجع. اختبار البحث عن كلمة RLS داخل source لا يثبت العزل؛ المطلوب تنفيذ استعلامات بصفة authenticated والتحقق من الصفوف والأخطاء.

## 5. الحالات الحدية ومعيار الإغلاق

الكتالوج يحتوي profiles مشتركة تشمل الفارغ/التحميل/الخطأ، إدخال غير صالح، تكرار، جلسة منتهية، انقطاع شبكة، API failure، timeout، تحديث متزامن، نجاح جزئي، بيانات كبيرة، سجلات محذوفة ومؤرشفة. لكل قصة معيارا قبول محددان إضافة إلى هذه المصفوفة؛ إن كانت حالة غير منطبقة يسجل QA السبب بدل الإشارة إلى اجتيازها.

كل قصة UI تحتاج عربي RTL وإنجليزي LTR، أحجام 360/768/1440، keyboard/focus، وعدم خلط تنسيق التاريخ مع منطقة حسابه. كل قصة مالية تحتاج مثال حساب مستقل، source reference وpolicy version، وعدم تعديل snapshot مقفلة. كل مورد يحتاج رفض tenant آخر وتحققًا من scope والحقول.

**Done** يتطلب كودًا مراجعًا، نتائج اختبارات مرتبطة بـSHA، واستعادة/ترحيل موثقة عند اللزوم. `implemented_local` يعني تحققًا محليًا فقط؛ `deployed_staging` و`accepted_for_production` حالتان منفصلتان مع دليل.

| المصدر                          | GitHub Issues / Projects                             | Jira / Linear                                      |
| ------------------------------- | ---------------------------------------------------- | -------------------------------------------------- |
| `story.id`                      | بادئة ثابتة في العنوان؛ تستخدم لمنع الاستيراد المكرر | External ID أو حقل مرجع ثابت                       |
| `title_ar` و`user_story`        | title وbody من JSONL جاهزان                          | Summary/Title وDescription                         |

| `technical_tasks` و`test_cases` | checklists في body                                   | subtasks/test management بعد قرار الفريق           |

يُستورد Epic أولًا، ثم القصص، ثم روابط التبعية باستخدام خريطة IDs؛ أدوات إدارة العمل لا تشترك في صيغة parent موحدة. لا تستبدل `RM-P1` بمعرف sprint حقيقي، ولا أسماء وظائف بأشخاص افتراضيين. البحث عن بادئة `[TEN-001]` ونظائرها يسبق أي إنشاء مكرر. لا توجد credentials أو أسماء مستلمين في ملف الاستيراد.

## 7. فجوات العقود التي كشفها الربط

- الكتالوج الحالي يضم 85 endpoint؛ عقود تفويض/إدارة permissions والفوترة والفواتير والمنصة والتحليلات وSSO ليست مكتملة فيه. القصص المعنية تحمل `api_refs: []` ومهام عقد واضحة بدل اختلاق endpoint موجود.
- أمثلة أرقام الشاشات في PART 16 كانت نطاقات تخطيط تقريبية؛ هذا الكتالوج يربط القصص بمعرفات PART 7 الفعلية، مثل S055 للحضور وS081 للرواتب وS137 للتدقيق.
- `tenant_memberships` في PART 3 و`memberships` في PART 10 يشيران إلى علاقة واحدة؛ PART 18 سيثبت الاسم المادي ويحدث alias قبل migration.
- موعد حجز الإجازة يجب أن يثبت عند submit كي لا يُصرف الرصيد مرتين. صياغة PART 9 العامة عن الحجز عند الاعتماد تحتاج تسوية قبل LEV-001؛ الاعتماد ينقل الحجز إلى used في معاملة واحدة.

هذه فجوات محددة قابلة للحل ضمن المهام؛ لا تؤخر إعداد الأساس المعزول. PART 18 يسجل نتيجة أول دفعة عند تنفيذها.
