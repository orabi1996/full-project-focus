# دفعة سلامة الرواتب والخدمة الذاتية

## التغييرات

- إصلاح أخطاء ESLint الستة التي كانت تمنع تشغيل الاختبارات والبناء.
- حفظ المسيّر والتفاصيل وتوزيع السلف في معاملة PostgreSQL واحدة؛ فشل إعادة الاحتساب يحافظ على المسودة السابقة.
- قسط مستقل لكل سلفة، لا يتجاوز رصيدها، محفوظ عند احتساب المسيّر. لا يُخصم إجمالي أقساط الموظف من كل سلفة.
- قفل المسيّر قبل تجهيز الدفعات. منع تكرار الموظف في مجموعات رواتب متداخلة لنفس الشهر.
- تأكيد الصرف يسجّل تحويلًا أتمّه المستخدم خارج النظام. يتطلب مرجع البنك وتأكيد اكتمال دفعات المسيّر بالكامل، ويحدث الرصيد الدفتري والأقساط والدفعات وحالة المسيّر في معاملة واحدة.
- إعادة نفس التأكيد لا تكرر الخصم؛ مرجع آخر لنفس المسيّر يُرفض، وإعادة استعمال المرجع لحساب البنك نفسه في مسيّر آخر تُرفض.
- صلاحية تسجيل التأكيد للمسؤول المالي أو مسؤول المنشأة أو المسؤول العام. صلاحية إعداد الرواتب وحدها لا تكفي للتأكيد.
- ملف التحويل CSV يصدّر الدفعات غير المدفوعة فقط ويستخدم حساب المنشأة المختار؛ يبقى ملفًا للمراجعة وليس اعتمادًا لصيغة بنك أو WPS.
- الخدمة الذاتية تعرض أحدث قسيمة معتمدة للموظف المرتبط بالحساب، وأرصدة إجازاته فقط. الحساب غير المرتبط لا يستعير أول موظف في القائمة.
- طلب شهادة الراتب يُحفظ في الطلبات للاعتماد؛ أزيلت رسائل الإصدار الفوري وQR الوهمية والرواتب والتواريخ الثابتة.

## ترتيب الإطلاق

1. طبّق `supabase/migrations/20260908120000_atomic_payroll_confirmation.sql` على قاعدة اختبار مرتبطة بالمشروع.
2. اختبر مستخدم موظف، ومعد رواتب، ومسؤول مالي بحسابات حقيقية، مع سياسات RLS الخاصة بالمنشأة.
3. بعد التحقق، طبّق الترحيل نفسه على قاعدة الإنتاج **قبل نشر كود الواجهة والخادم**؛ المسار الجديد يعتمد على الدوال الجديدة ولا يرجع إلى المسار القديم عند غيابها.
4. انشر كود هذه الدفعة، ثم نفّذ دورة احتساب → اعتماد وقفل → تجهيز دفعات → تصدير → تنفيذ خارج النظام → تسجيل المرجع.

لا ينفذ هذا التحديث تحويلًا بنكيًا، ولا يثبت اتصال البنك، ولا يطبق ترحيلًا على قاعدة الإنتاج تلقائيًا.

### المسيّرات السابقة

- المسودات السابقة يمكن إعادة احتسابها للحصول على توزيع أقساط محفوظ.
- المسيّرات المقفلة سابقًا التي تحتوي خصم سلف دون توزيع محفوظ تحتاج مراجعة وتسوية بيانات من المسؤول المختص قبل التأكيد. لا توجد تعبئة تلقائية تخمينية ولا فك قفل آلي.
- المسيّرات المدفوعة سابقًا لا تُعاد معالجتها. أخطاء الاسترداد التاريخية تحتاج مراجعة مستقلة؛ هذا التحديث لا يصحح أرصدة قديمة تخمينًا.
- تسجيل التأكيد في هذه الدفعة للمسيّر الكامل، لا للدفعات الجزئية؛ الحالات الجزئية السابقة تحتاج مراجعة منفصلة.

## التحقق

- `npm run lint`
- `npm run typecheck`
- `npm run test:coverage`
- `npm run build`
- `npm run test:e2e`

تختبر `src/tests/payroll-transactions.test.ts` الدوال الفعلية من ملف الترحيل على PostgreSQL محلي عبر PGlite: توزيع سلف متعددة، تكرار التأكيد، rollback، رفض فقد التوزيع، الرصيد غير الكافي، الحالات غير المسموحة، تداخل المجموعات، الصلاحيات وإعادة استخدام المرجع. تستخدم الاختبارات مخططًا مصغرًا يمثل الجداول السابقة؛ لا تُعد اختبارًا لكل ترحيلات Supabase أو سياسات الإنتاج. اختبارات الواجهة الحالية تستخدم Demo.

## بقية خطة الاستكمال

لم تدخل في هذه الدفعة: التخزين الدائم لخزينة المستندات، حفظ التفويضات وحذف مسارات الاعتماد، مراجعة صلاحيات جميع الوحدات على قاعدة حقيقية، والتكامل البنكي الفعلي. تبقى لها الأولوية بعد نشر دفعة سلامة الرواتب والتحقق منها.
