## 1. النتيجة الفعلية

أضيف سجل للشركات والعضويات والإعدادات، مع endpoint `GET /api/v1/me` يعيد سياقًا مرتبطًا بهوية تحقق منها الخادم. العضوية لا تمنح صلاحيات HR المالية أو الإدارية؛ صلاحيات الموارد والنطاقات وفصل المهام تأتي في IAM-002.

| العنصر               | التنفيذ                                                                       | الحدود                                                                                 |
| -------------------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `tenants`            | UUID، slug فريد، اسم قانوني، حالة، أرشفة وversion                             | لا تُستنتج شركة SaaS من بيانات `companies` القديمة                                     |
| `tenant_memberships` | مستخدم Auth + tenant، حالة ونافذة صلاحية `[starts_at, ends_at)`               | لا يستطيع المتصفح إنشاء العضوية أو تحديثها أو حذفها                                    |
| `tenant_settings`    | لغة ar/en، منطقة زمنية معروفة في PostgreSQL، رمز عملة                         | لا يوجد افتراض تلقائي لبلد أو عملة؛ التحقق من رمز العملة شكلي، وسياسة البلد مهمة لاحقة |
| RLS + grants         | قراءة بيانات الشركة وعضوية المستخدم نفسه، وسحب الرؤية عند التعليق أو الانتهاء | هذه الضوابط تخص الجداول الثلاثة الجديدة؛ جداول HR القديمة لم تُرحّل بعد                |
| `GET /api/v1/me`     | تحقق Auth، اختيار tenant، DTO محدود، أخطاء AR/EN وno-store                    | لا قائمة شركات كاملة أو دعوات أو تبديل جلسة أو صلاحيات أعمال ضمن هذه الدفعة            |

لا تعمل شاشة متعددة العملاء بأمان بمجرد إضافة هذا السجل. يلزم TEN-003 لربط ملكية الجداول القديمة، ثم RLS واختبارات لكل مجال. كذلك لا يثبت هذا العمل صحة الرواتب أو الامتثال المحلي أو جاهزية الإنتاج.

## 3. عقد السياق

```http
GET /api/v1/me
Authorization: Bearer <user-access-token>
X-Tenant-Id: <tenant-uuid>
Accept-Language: ar
```

`X-Tenant-Id` محدد اختيار فقط؛ لا يثبت العضوية. إذا كانت هناك عضوية واحدة مؤهلة يمكن حذف العنوان. عند تعدد العضويات يجب الاختيار صراحة، ولا نستخدم أول صف عشوائيًا. يقرأ المحوّل صفين كحد أقصى لتمييز صفر/واحدة/متعددة؛ قائمة اختيار كاملة لها query مستقلة لاحقًا.

```json
{
  "data": {
    "user_id": "10000000-0000-4000-8000-000000000001",
    "membership": { "id": "30000000-0000-4000-8000-000000000001" },
    "tenant": {
      "id": "20000000-0000-4000-8000-000000000001",
      "slug": "alpha",
      "legal_name": "منشأة اختبار ألف",
      "status": "active"
    },
    "settings": { "locale": "ar", "timezone": "Asia/Riyadh", "currency_code": "SAR" }
  },
  "meta": { "request_id": "40000000-0000-4000-8000-000000000001" }
}
```

هذه قيم fixtures اصطناعية. `settings` يمكن أن تكون `null` أثناء التهيئة؛ المستهلك لا يستنتج منها سياسة حساب أو عملة بديلة. الاستجابة snapshot عرض وليست credential: يجب إعادة حل العضوية قبل كل command جديد.

| HTTP | code                   | السلوك                                                                              |
| ---- | ---------------------- | ----------------------------------------------------------------------------------- |
| 405  | `method_not_allowed`   | طريقة غير GET/HEAD؛ يعيد Allow ولا يصل لقاعدة البيانات                              |
| 401  | `unauthorized`         | غياب bearer أو فشل التحقق من الجلسة؛ لا قراءة عضويات                                |
| 422  | `validation_error`     | معرف tenant ليس UUID صالحًا                                                         |
| 409  | `tenant_required`      | أكثر من عضوية مؤهلة دون اختيار                                                      |
| 403  | `tenant_access_denied` | لا عضوية سارية للشركة المطلوبة؛ لا كشف لوجود شركة أخرى                              |
| 503  | `service_unavailable`  | فشل Auth/DB المؤقت، schema غير مطبقة أو transport غير صالح؛ لا بيانات تجريبية بديلة |

تحتوي استجابة الخطأ على `error.code/message_key/message/retryable/request_id`. يولد الخادم request ID، ويضعه أيضًا في header، دون الوثوق بنص يرسله العميل. جميع الردود تحمل `Cache-Control: private, no-store` و`Vary` للهوية والاختيار واللغة. لا تُرجع رسائل PostgreSQL أو أسرار المزود.

## 4. قرارات الثقة والصلاحيات

1. `auth.getUser(token)` يتحقق من المستخدم عبر Auth؛ لا نفك JWT ونصدق محتواه محليًا ولا نقبل `user_id` أو `role` من query/header. [مرجع Supabase](https://supabase.com/docs/reference/javascript/auth-getuser).
2. استعلام العضوية يحمل bearer المستخدم والمفتاح العام فقط. لا يستورد service-role client، ويحصر الأعمدة المعادة، ويتحقق من shape عبر Zod.
3. الجداول الجديدة تفعل RLS وFORCE RLS وتسحب grants الافتراضية من PUBLIC/anon/authenticated، ثم تمنح authenticated القراءة وحدها. الجمع بين grants والسياسات مقصود لأنهما طبقتان مختلفتان. [مرجع RLS في Supabase](https://supabase.com/docs/guides/database/postgres/row-level-security).
4. تسلسل سياسات القراءة غير دائري: settings → tenants → عضويات المستخدم نفسه. لا توجد SECURITY DEFINER دالة لتجاوز هذه القراءة.
5. service_role والمشرف الموثوق يستطيعان provisioning؛ امتلاك هذه الصلاحيات يتجاوز حدود مستخدم التطبيق، ولا يُسمح بوصول مفاتيحهما إلى المتصفح. [PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).
6. يبقى سجل عضوية المستخدم نفسه قابلًا للقراءة عند تعليق tenant، لكن صف tenant وإعداداته واستجابة `/me` تختفي لأن query يستخدم inner join. لا تُعرض عضويات الآخرين.

## 5. التهيئة والترحيل والتراجع

تُضاف migration إلى مسار الإصدار الطبيعي بعد مراجعة staging. لا توجد أوامر اتصال أو مفاتيح إنتاج في المستودع. لا تُشغّل migration تلقائيًا عند طلب `/me`؛ غياب الجداول يعيد 503 عامًا.

خطوات التهيئة التشغيلية المطلوبة في بيئة اختبار معزولة:

1. تشغيل migrations بالترتيب في نسخة Supabase اختبارية ومراجعة grants والبيانات القديمة.
2. إنشاء مستخدمَي Auth اصطناعيين، ثم شركتين وإعداداتهما وعضويتيهما بواسطة operator مخول داخل transaction. يوثق معرف إجراء التهيئة؛ لم تنفذ هذه الخطوة على خدمة عميل.
3. التحقق من `/me` بتوكن كل مستخدم، وطلب tenant الآخر، والتعليق وانتهاء العضوية. يمنع أي onboarding ذاتي حتى تنفيذ IAM-001 وضوابط إنشاء العضوية وتدقيقه.
4. لا تُمنح memberships صلاحيات legacy. تُعد خريطة tenant_legacy_map وتراجع الصفوف اليتيمة قبل TEN-003.

**التراجع:** يمكن إعادة كود التطبيق للإصدار السابق مع إبقاء الجداول المضافة؛ لا يعتمد الكود القديم عليها. تُعطل route/feature عند الحاجة، ويُعالج schema بفحص أو forward migration. لا تحذف الجداول إذا بدأت تخزين عضويات؛ يحتفظ بتاريخ البيانات. لا rewrite أو force push للتاريخ المنشور.

**توحيد الاسم:** `tenant_memberships` هو الاسم المادي الذي اختارته PART 3. حُدث alias واسم الكيان في PART 10، مع بقاء `memberships` وصفًا منطقيًا للعلاقة نفسها. `membership_roles` سيأتي لاحقًا؛ السجل الحالي لا يحتوي catalog أدوار مُفعّلًا.

الأوامر القابلة لإعادة التنفيذ: `npm ci` ثم `npm run typecheck` و`npm run test:coverage` و`npm run lint` و`npm run build`. يثبت lockfile `@electric-sql/pglite` عند `0.5.8` كتبعية تطوير فقط، ولا يدخل التطبيق التشغيلي. الاختبارات الجديدة تعمل ضمن quality workflow القائمة ولا تحتاج حساب DB خارجي.

اختبارات PGlite تنفذ PostgreSQL فعليًا داخل العملية، وتُنشئ أدوارًا و`auth.uid()` اصطناعية وgrants افتراضية لاختبار migration. [PGlite](https://pglite.dev/docs/). **لا تمثل تشغيل سلسلة migrations القديمة كاملة أو PostgREST أو جلسة Supabase حية**؛ هذه بوابات staging باقية. اختبارات HTTP للمحوّل تستخدم transport اصطناعيًا ولا ترسل توكنات إلى خدمة عميل. لم يُعد تشغيل اختبارات واجهة المتصفح لأن هذه الدفعة لا تغير واجهة المستخدم.

تم أيضًا فحص route عبر HTTP على Vite محلي: GET وHEAD دون جلسة يعيدان 401، وPOST يعيد 405 مع `Allow: GET, HEAD`. HEAD بلا body. يجيب Vite عن OPTIONS مسبقًا بـ204 في بيئة التطوير؛ لذلك لا يُعد هذا اختبار CORS لإصدار الإنتاج. لم تُرسل بيانات Auth إلى خدمة عميل.
